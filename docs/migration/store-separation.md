# 이행 계획: 매장 단위 상품 상태를 Store 서비스로 옮기기

> 문서별 역할과 수정 순서는 [문서 안내](../README.md)를 참고한다. 결정과 이유는 [ADR-0020](../adr/0020-store-owns-store-product-state.md)에 있고, 이 문서는 **어떤 순서로 옮기고 언제 옛 기능을 지우는가**만 다룬다.

매장별 진열 설정, 판매 가능 여부, 노출 판단, 노출 현황은 Catalog에서 Store 서비스로 이전한다. 한 번에 바꾸지 않고 단계별로 한다. 이행이 끝나기 전까지 현재 구조(요구사항 2·3장, 1.10)는 유효하다.

## 전제

- **Catalog에 운영 데이터가 없다.** 운영 전이므로 `store_display_settings`, `store_product_availabilities`를 Store로 옮길 데이터가 없다. 재고 이벤트 소비도 Catalog에 구현된 적이 없다.
- **Store는 아직 운영에 올라가지 않았다.** 점주와 손님의 트래픽도 아직 없다.
- 운영 데이터가 있었다면 필요했을 절차는 [부록](#부록-운영-데이터가-있을-때의-이행)에 둔다. 이 전제가 깨지면(Store보다 먼저 Catalog에 매장 데이터가 쌓이면) 부록을 따른다.

## 단계와 버전

| 단계 | 하는 일 | Catalog 버전 | 상태 |
|---|---|---|---|
| 1. Catalog 확장 | 상품 이벤트 발행, Store용 조회 API, 카테고리 노출 순서, 대상 매장 확인(Store 호출). 옛 매장 기능은 그대로 | v0.2.0 | 코드 완료(#134, #139, #140, #141). **실연동 검증과 릴리스 전** |
| 2. Store 구독과 복제본 채우기 | Store가 이벤트를 구독하고 전체 상품 상태 목록으로 복제본을 채운 뒤 일치를 확인 | (같음) | Store 구현 중 |
| 3. 전환 | 점주 요청을 Store가 직접 처리하고 손님 메뉴를 연다. Catalog의 옛 매장 API 호출이 없어진다 | (같음) | |
| 4. 제거 | Catalog에서 `store`·`exposure` 모듈, 두 테이블, 매장 대상 API를 지운다([#138](https://github.com/dozycoffee/dozy-catalog-api/issues/138)) | v0.3.0 | 전환이 확인된 뒤 |
| (운영 배포) | 첫 운영 배포 시점에 1.0.0 여부를 정한다. 4단계가 끝난 구조(옛 매장 API 없이 이벤트·조회 API 계약만 남음)가 후보다 | 1.0.0? | |

버전 규칙은 [README 배포](../../README.md#배포)를 따른다(0.x 동안 기능 추가와 호환을 깨는 변경은 minor). 4단계는 엔드포인트를 지우므로 minor를 한 번 더 올린다.

## 1단계 완료 조건

- [ ] **Kafka**: 브로커와 토픽 `dozy.catalog.product`가 있다. 파티션 수는 처음에 정하고 늘리지 않는다(키와 파티션의 대응이 바뀌면 순서가 깨진다). 운영 브로커가 토픽 자동 생성을 끄고 있으면 미리 만든다. 보존 기간은 Store가 구독을 시작하기까지의 지연보다 길게 둔다([이벤트 계약 8절](../events/product.md#8-운영))
- [ ] **Auth**([#77](https://github.com/dozycoffee/dozy-catalog-api/issues/77)): audience `catalog`, 역할 `catalog:admin`(본사 직원)·`catalog:store_agent`(Store의 system client), Catalog의 system client `svc-catalog`와 Store의 `store:catalog_agent` 역할
- [ ] **설정**: Catalog의 `KAFKA_BOOTSTRAP_SERVERS`, `STORE_BASE_URL`, `DOZY_AUTH_CLIENT_SECRET`. 셋 중 하나라도 없으면 prod가 기동하지 않는다
- [ ] **실연동 검증**: Catalog, Store, Kafka, dozy-auth를 함께 띄워 아래를 확인한다
   - 상품 등록·활성화·단종·판매 범위 변경·삭제 이벤트가 Store 복제본에 반영된다(예약 적용으로 바뀐 경우 포함)
   - Store가 부르는 조회 API 네 개의 응답을 Store가 읽는다. 값이 없는 필드는 이벤트가 생략하고 API가 `null`로 주는 차이를 Store가 같게 본다
   - Catalog의 판매 범위 변경이 Store의 대상 매장 확인을 통과하고, 없는 매장·폐점 매장은 거부된다
   - 같은 이벤트를 다시 받거나 순서가 바뀌어도 복제본이 틀어지지 않는다
- [ ] 성능 선행: [#130](https://github.com/dozycoffee/dozy-catalog-api/issues/130). 측정은 [#142](https://github.com/dozycoffee/dozy-catalog-api/issues/142)

위가 끝나면 v0.2.0 태그를 붙인다. 태그를 붙이면 그 커밋의 이미지에 `0.2.0`이 덧붙을 뿐 다시 빌드하지 않고, 한 번 붙인 버전 태그는 다른 이미지로 바꾸지 않는다([ADR-0019](../adr/0019-container-image-with-dockerfile-and-tag-release.md)). 연동이 검증되기 전에는 `main`·`sha-…` 이미지로 통합 검증을 한다.

### 배포 순서와 호환

- **Catalog를 먼저 배포한다.** 이벤트는 Kafka에 쌓이므로 구독자가 없어도 유실되지 않는다.
- 새 마이그레이션(V5 아웃박스, V6 카테고리 순서)은 **추가만 하고 옛 코드와 함께 돌 수 있다.** V6의 새 컬럼은 `DEFAULT 0`이라 옛 버전 앱이 행을 넣어도 깨지지 않는다. 롤링 배포가 안전하다.
- 옛 환경에서 올릴 때는 위 설정 세 가지가 먼저 있어야 한다. 이것은 API가 아니라 **배포 설정의 비호환**이다.
- Store가 운영에 없으면 Catalog의 판매 범위 변경은 `503 STORE_SERVICE_UNAVAILABLE`로 거부된다(확인 없이 통과시키지 않는다).

## 2단계: Store 구독과 복제본 채우기

1. Store가 `dozy.catalog.product`의 구독을 **먼저** 시작한다(소비자 그룹 `store.product-replica`).
2. Store가 전체 상품 상태 목록(`GET /internal/product-states`)으로 복제본을 채운다. 이벤트와 순번 비교로 같은 규칙을 쓰므로 둘이 겹치거나 순서가 섞여도 최신 상태가 남는다.
3. **일치 확인**: Store 복제본의 상품 수와 Catalog의 상품 수(삭제된 것 제외)가 같고, 샘플의 상태·판매 범위·순번이 같다.

이 단계는 Store 쪽 변경만 일으키고 Catalog와 사용자에게는 영향이 없다. 틀리면 Store의 복제본을 비우고 다시 채운다.

## 3단계: 전환

운영 전이라 옮길 데이터와 되돌릴 사용자가 없어서 **점진 전환과 섀도우 비교를 생략한다.**

- Store가 점주의 진열·숨김·품절 요청을 자기 DB로 처리하고, 손님 메뉴를 연다. Store는 더 이상 Catalog의 `/internal/stores/**`를 부르지 않는다.
- 전환 직후 Catalog의 옛 매장 API 호출이 없는지 확인한다(액세스 로그, `http_server_requests`의 경로 태그).
- **롤백**: 운영 전에는 전환으로 쌓이는 매장 데이터가 없으므로 되돌릴 것이 없다. 문제가 있으면 Store를 고쳐 다시 배포한다. 옛 Catalog 매장 기능은 4단계 전까지 남아 있지만, Store의 설계(Store ADR-0001)는 자기 DB를 원본으로 삼으므로 그 기능으로 되돌아가는 경로를 두지 않는다.

## 4단계: 제거 (v0.3.0)

**조건**: Store가 운영에 올라 점주·손님 트래픽이 전환되었고, Catalog의 옛 매장 API 호출이 한동안 없다. 먼저 지우면 그 사이 매장 기능이 아무 데도 없다.

**순서**

1. 문서를 먼저 고친다. 요구사항 2·3장과 1.10은 Store 참조로 줄이고, 시나리오 S6·S7, 도메인 모델(BC 경계, 애그리거트 지도, 도메인 이벤트), ERD, API 명세(`store.md`, `exposure.md`), 아키텍처 미정 사항을 같은 순서(요구사항 → 시나리오 → 도메인 모델 → ERD)로 고친다.
2. 코드를 지운다: `store`·`exposure` 모듈, 매장 내부 API, 본사의 매장 상품 조회와 노출 현황 API, 재고 이벤트 소비, `catalog.exposure.store-ids` 설정.
3. 테이블 삭제는 **별도 마이그레이션**으로 한다(`store_display_settings`, `store_product_availabilities`). 코드를 지운 버전이 배포된 뒤에 올려, 옛 버전이 돌고 있는 동안 테이블이 없어지지 않게 한다.
4. 부하테스트 도구에서 옛 매장 시나리오를 지운다(#142).

## 옛 기능의 상태

4단계까지 옛 매장 기능은 **더 이상 키우지 않는다.** 새 기능을 얹거나 성능을 고치거나 부하를 재지 않는다. 각 문서에 "제거 예정" 표시를 달아 두었다.

## 부록: 운영 데이터가 있을 때의 이행

Catalog에 매장 데이터가 쌓인 뒤 이행한다면 2단계와 3단계 사이에 **데이터 이전과 섀도우 비교**가 들어간다. 지금은 필요 없다.

| 단계 | 하는 일 | 되돌리기 |
|---|---|---|
| 데이터 이전 | `store_display_settings`, `store_product_availabilities`를 Store로 옮긴다. 폐점한 매장과 없는 상품의 행은 옮기지 않고, 진열 순서·숨김·수동 품절은 같은 의미로 변환한다. 도구는 여러 번 돌려도 같은 결과가 나오게(upsert) 한다. 행 수와 매장별 샘플로 검증한다 | Store 데이터를 지우고 다시 이전 |
| 섀도우 비교 | 점주·손님 트래픽은 그대로 두고, Store가 자기 규칙으로 계산한 노출 결과를 Catalog의 옛 결과와 비교만 한다. Store에는 영업 상태 단계(0단계)가 있어 폐점·휴업 매장에서 차이가 나는 것이 정상이다. 그 밖의 차이는 원인을 찾는다 | 영향 없음 |
| 전환 | **매장 단위로 점진적으로** 한다(소수 매장 → 지역 → 전체). 매장 하나의 쓰기는 한 시점에 한 곳만 받는다. 마지막 증분을 옮기려고 **짧은 쓰기 동결**(새벽 몇 분)을 한다: 옛 매장 쓰기 API를 읽기 전용으로 바꾸고, 마지막 변경(`updated_at` 기준)을 옮긴 뒤 Store를 켠다 | 아래 |
| 관찰 | 이벤트 지연, 오류율, 노출 불일치 신고, 옛 API 호출량 0 | 옛 기능이 살아 있어 가능 |
| 제거 | 호출 0이 N주 지속된 뒤 4단계 | 백업에서 복구 |

**롤백이 어렵다.** 전환 뒤 Store에서 바뀐 설정은 Catalog 테이블에 없으므로 단순히 옛 기능으로 돌아갈 수 없다. 관찰 기간 동안 **역이전 도구**(Store → Catalog)를 준비해 두어야 한다. 판매 범위 변경으로 정리된 설정도 포함한다. 점진 전환은 문제가 소수 매장에서 드러나게 해서 되돌릴 대상을 줄인다.

이때 Catalog에 필요한 개발은 두 테이블의 내보내기, 옛 매장 쓰기 API의 읽기 전용 스위치, 옛 API 호출량 지표, 역이전 도구다. 운영 전인 지금은 만들지 않는다.
