# 상품 이벤트 계약 (`dozy.catalog.product`)

> 문서별 역할과 수정 순서는 [문서 안내](../README.md)를 참고한다. 상태: **초안**(Catalog의 발행은 구현됨, Store의 구독 확인 전). 결정의 이유는 [ADR-0020](../adr/0020-store-owns-store-product-state.md)(Store가 매장 상태를 소유함), [ADR-0021](../adr/0021-kafka-outbox-for-product-events.md)(Kafka와 아웃박스)에 있다.

Catalog가 다른 서비스에 알리는 **상품 상태**의 계약이다. 구독자(지금은 Store)는 이 이벤트로 판단에 필요한 상품 상태를 복제해 둔다. 이름·가격·옵션 같은 표시용 정보는 이 이벤트에 없고 조회 API로 받는다. 메시지 형식은 사내 공통 MSA 이벤트 형식을 따른다.

## 1. 개요

| 항목 | 내용 |
|---|---|
| 토픽 | `dozy.catalog.product` (집계 = 상품) |
| 메시지 키 | `productId`의 문자열. 같은 상품의 이벤트는 순서가 지켜진다 |
| 값 | JSON 하나. Kafka 헤더는 쓰지 않는다 |
| 발행자 | Catalog 하나뿐 |
| 종류 | **상태 이벤트**. 바뀐 부분이 아니라 상품 상태 전체를 담는다 |
| 전달 보장 | at-least-once. 유실되지 않고, 중복되거나 순서가 바뀌어 도착할 수 있다 |
| 구독자 | [구독자와 소비자 그룹](#구독자와-소비자-그룹) 참고 |

### 구독자와 소비자 그룹

- 이 토픽은 여러 서비스가 읽어도 된다. 메시지는 읽어도 지워지지 않고 소비자 그룹마다 읽은 위치가 따로 있으므로, 구독자가 늘어도 다른 구독자가 못 받는 일이 없고 Catalog는 바뀌지 않는다.
- **서비스마다 자기 소비자 그룹을 쓴다.** 이름은 `{구독 서비스}.{용도}`다(예: `store.product-replica`). 같은 그룹을 쓰는 인스턴스는 메시지를 나눠 가지므로, 한 서비스의 인스턴스끼리는 그룹을 공유하고 **다른 서비스와는 공유하지 않는다.**
- 구독하기 전에 아래 표에 올린다.

| 구독 서비스 | 소비자 그룹 | 용도 | 상태 |
|---|---|---|---|
| Store | `store.product-replica` (가칭, Store가 확정) | 판단용 상품 상태 복제(노출 판단, 판매 범위 정리, 노출 현황) | 구독 구현 전 |

- 계약을 바꿀 때 호환되는 변경([7절](#7-변경-규칙))은 알리지 않아도 되지만, 깨지는 변경은 이 표의 **모든 구독자**와 전환 일정을 정한다.
- 구독자에게 이 계약의 값이 부족하면(예: 가격이나 옵션이 필요) 이 토픽의 값을 늘리지 않는다. 조회 API를 쓰거나, 값이나 접근 범위가 다르면 별도 토픽으로 정한다.

## 2. 메시지

```json
{
  "eventId": "0199a3c4-7b2e-7c1a-9f3d-2b6e8a1c4d5f",
  "eventType": "PRODUCT_STORE_SCOPE_CHANGED",
  "eventVersion": 1,
  "occurredAt": "2026-10-14T10:00:00+09:00",
  "source": "catalog",
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "data": {
    "productId": 1024,
    "sku": "DZ-00001024",
    "status": "ACTIVE",
    "storeScope": { "kind": "LIMITED", "targetStoreIds": [12, 35, 107] },
    "tracksInventory": false,
    "sequence": 42
  }
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `eventId` | string (UUID) | 예 | 이벤트 하나의 고유 ID. UUID v7. 다시 발행해도 같은 값이다. 구독자의 중복 제거 키 |
| `eventType` | string | 예 | [4절](#4-이벤트-종류) 참고 |
| `eventVersion` | int | 예 | 지금은 `1`. 호환되지 않는 변경에만 올린다([7절](#7-변경-규칙)) |
| `occurredAt` | string | 예 | 이벤트를 아웃박스에 기록한 시각(오프셋 포함 ISO-8601). 업무 기준 시간대(`+09:00`)로 쓴다. Kafka 발행 시각이 아니다 |
| `source` | string | 예 | 항상 `catalog` |
| `traceparent` | string | 아니오 | W3C Trace Context. 요청 안에서 만든 이벤트에만 있다. 예약 적용 배치처럼 요청이 없는 경로의 이벤트에는 없다 |
| `data` | object | 예 | [3절](#3-data) |

JSON 규칙은 공통 형식을 따른다. 필드 이름은 camelCase이고, 값이 `null`이면 필드를 보내지 않는다(구독자는 없는 것과 `null`을 같게 본다). `0`, `""`, `[]`는 그대로 보낸다.

## 3. `data`

상품 상태 전체다. 어떤 `eventType`이든 같은 모양이다(삭제는 [4절](#4-이벤트-종류) 참고).

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `productId` | number | 예 | 상품 ID. 등록 순으로 커진다(본사 등록 순으로 쓸 수 있다) |
| `sku` | string | 아니오 | 상품의 SKU(`DZ-00000123`). 등록 때 시스템이 부여하지만 과거 데이터에는 없을 수 있어 선택이다 |
| `status` | string | 예 | `DRAFT`, `ACTIVE`, `DISCONTINUED` ([요구사항 1.1, 1.3](../requirements.md)) |
| `storeScope` | object | 예 | 판매 범위 ([요구사항 1.5](../requirements.md)) |
| `storeScope.kind` | string | 예 | `ALL`(모든 매장) 또는 `LIMITED`(대상 매장만) |
| `storeScope.targetStoreIds` | number[] | `LIMITED`일 때만 | 대상 매장 ID. `LIMITED`이면 항상 있고(비어 있을 수 있다) `ALL`이면 없다. 빈 `LIMITED`는 어떤 매장도 포함하지 않는다 |
| `tracksInventory` | boolean | 예 | 재고 추적 상품인지. 등록 뒤 바뀌지 않는다 |
| `sequence` | number | 예 | 상품별 순번. [5절](#5-순번과-구독자의-처리) 참고 |
| `deleted` | boolean | 삭제 이벤트에만 | 항상 `true` |

## 4. 이벤트 종류

구독자는 종류와 관계없이 `data`의 상태로 복제본을 교체한다. 종류는 왜 바뀌었는지 알리는 용도다. 모르는 종류는 로그를 남기고 건너뛴다.

| `eventType` | 발행 시점 | 비고 |
|---|---|---|
| `PRODUCT_REGISTERED` | 상품 등록. 항상 `DRAFT` | `sequence`는 `0` |
| `PRODUCT_ACTIVATED` | 활성화(`DRAFT → ACTIVE`, `DISCONTINUED → ACTIVE`). 즉시 또는 예약 적용 | 재활성화도 같은 종류다 |
| `PRODUCT_DISCONTINUED` | 단종(`ACTIVE → DISCONTINUED`). 즉시 또는 예약 적용 | |
| `PRODUCT_STORE_SCOPE_CHANGED` | 판매 범위 변경. 즉시 또는 예약 적용 | 현재 구현은 값이 같아도(같은 범위로 다시 지정) 발행한다 |
| `PRODUCT_DELETED` | 상품 삭제(`DRAFT`만 가능, [요구사항 1.11](../requirements.md)) | 이후 이 상품의 이벤트는 없다 |

- **삭제 이벤트**의 `data`는 `productId`, `sequence`, `deleted: true`만 담는다. 구독자는 행을 지우지 않고 삭제로 표시한다. 늦게 도착한 오래된 이벤트로 상품이 되살아나지 않게 하기 위해서다.
- 이름, 가격, 옵션, 카테고리, 태그, 상품 그룹의 변경은 이벤트가 없다. 구독자가 복제하는 값이 아니기 때문이다.
- 한 번의 변경(한 트랜잭션)에서 한 상품에 대한 이벤트는 **하나**다. 여러 변경이 한 트랜잭션에서 겹치면 마지막 상태를 담은 이벤트 하나를 낸다.

## 5. 순번과 구독자의 처리

`data.sequence`는 같은 상품의 이벤트끼리 **뒤에 일어난 것이 항상 크다**. 값은 Catalog가 상품을 저장할 때마다 1씩 올리는 상품의 버전이다.

- 순번은 연속이 아니다. 이벤트가 없는 변경(예: 이름 수정)도 순번을 올리므로 건너뛴다. 구독자는 크기만 비교한다.
- 등록 이벤트가 `0`이고, 삭제 이벤트는 삭제 직전 버전에 1을 더한 값이다.
- 다른 상품의 순번과는 비교하지 않는다.

**구독자의 처리 규칙**

1. 같은 `eventId`를 이미 처리했으면 무시한다(중복 전달).
2. 복제본이 있고 `sequence`가 복제본의 순번보다 **크지 않으면** 무시한다(오래된 이벤트, 순서 역전, 다시 읽기).
3. 그 밖에는 `data`의 상태로 복제본을 통째로 교체한다. 종류에 따라 다르게 처리하지 않는다.
4. 삭제 이벤트는 복제본을 지우지 않고 삭제로 표시한다.
5. 모르는 필드는 무시한다. 필드가 없는 것과 `null`은 같다.

**순서**

- 같은 키의 순서는 같은 파티션 안에서만 지켜진다.
- 영구히 발행되지 못해 격리된 이벤트는 운영자가 다시 발행한다. 그동안 나간 뒤의 이벤트보다 **늦게 도착할 수 있다.** `eventId`는 같다. 위 규칙 2가 이 경우를 처리한다.

## 6. 처음 채우기와 다시 맞추기

구독자가 새로 뜨거나 복제본이 어긋나면 **전체 상품 상태 목록 조회 API**로 채운다. 응답의 각 상품은 이 문서의 `data`와 같은 모양이고 같은 `sequence`를 담는다. 구독자는 이벤트와 같은 규칙으로 반영한다(이벤트와 겹쳐도 `sequence` 비교로 안전하다). API 명세는 [API 문서](../api/README.md)에 추가한다(후속 작업).

## 7. 변경 규칙

| 변경 | 호환 | 방법 |
|---|---|---|
| `data`에 선택 필드 추가 | 호환 | `eventVersion`을 올리지 않는다. 변경 이력에 남긴다 |
| `eventType` 추가 | 호환 | 구독자는 모르는 종류를 건너뛴다 |
| 필드 삭제, 이름·타입·의미 변경, 필수 필드 추가 | 깨짐 | `eventVersion`을 올린다. 구독자와 전환 일정을 정하고 한동안 두 버전을 함께 발행한다 |
| 메시지 키 변경 | 깨짐 | 새 토픽 |

## 8. 운영

- **지연**: 아웃박스의 폴링 간격만큼 늦게 나간다. 단종·판매 범위 변경이 구독자에게 반영되기까지의 지연은 이 간격과 구독자의 처리 시간을 더한 값이다.
- **발행 빈도**: 상품 변경 빈도는 낮다. 예약 적용 배치가 같은 날 00시에 여러 상품을 적용하면 한꺼번에 수백 건이 나갈 수 있다.
- **메시지 크기**: `LIMITED` 상품은 대상 매장 목록 전체를 담는다. 매장 3,000개를 모두 대상으로 하면 ID만 약 20KB다. Kafka 기본 메시지 크기 한도(약 1MB) 안이지만 매장 수가 크게 늘면 다시 본다.
- **개인정보와 비밀값**은 담지 않는다. 사용자 토큰도 담지 않는다.
- 파티션 수, 보존 기간, 복제, 브로커 인증은 인프라에서 정한다. 파티션 수는 처음 정하고 늘리지 않는 것을 전제로 한다(키와 파티션의 대응이 바뀌면 순서가 깨질 수 있다).

## 9. 확인이 필요한 것

초안이라 Store와 확인해야 하는 항목이다.

| 항목 | 지금 계약 | 확인할 것 |
|---|---|---|
| `sequence`의 값 | 상품 버전(64비트 정수, 건너뜀) | 구독자가 정수 범위를 문제없이 다루는지 |
| 삭제 이벤트의 모양 | `productId`, `sequence`, `deleted` | 구독자가 더 필요한 값이 있는지 |
| 같은 범위로 다시 지정했을 때 | 현재 구현은 이벤트를 낸다 | 구독자가 변하지 않은 상태의 이벤트를 문제없이 받는지(순번이 올라가므로 교체된다). 안 내려면 도메인 쪽에서 막아야 한다 |
| 소비자 그룹 이름 | 구독자가 정한다 | Store가 정한 이름을 여기에 적을지 |
| 조회 API의 모양 | 6절 | 일괄 크기, 페이징 여부 |
