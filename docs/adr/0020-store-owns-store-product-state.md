# ADR-0020: 매장 단위의 상품 상태는 Store 서비스가 소유하고, Catalog는 상품 이벤트와 조회 API로 연동한다

- **상태**: 채택
- **날짜**: 2026-10-14
- **관련**: [ADR-0018](0018-partner-requests-through-store-service.md), ADR-0003, 0005, 0015(소유 이전으로 일부 대체), [도메인 모델](../domain-model.md) BC 경계, [미정 사항](../architecture/README.md#미정-사항)(Store 정보 로컬 투영), 이슈 #122, #123, #130, Store의 [ADR-0001](https://github.com/dozycoffee/dozy-store-api/blob/main/docs/adr/0001-store-owns-store-product-state.md)·[ADR-0002](https://github.com/dozycoffee/dozy-store-api/blob/main/docs/adr/0002-minimal-product-replica-with-full-state-events.md)·[ADR-0004](https://github.com/dozycoffee/dozy-store-api/blob/main/docs/adr/0004-public-customer-menu-for-all-channels.md), Store 요구사항 7장

## 맥락

지금은 Catalog가 매장 단위의 상품 상태를 소유한다. 매장별 진열 설정(`StoreDisplaySetting`), 판매 가능 여부(`StoreProductAvailability`, 재고 이벤트 투영 포함), 노출 판단(`ProductVisibilityPolicy`), 매장별 노출 현황(`exposure` 모듈)이다. 도메인 모델은 이를 "상품이 어떻게 판매되는가에 대한 관심사이지 매장이라는 개체 자체에 대한 관심사가 아니다"라고 보고 Catalog에 두었고, ADR-0003·0005·0015가 그 위에서 모델링과 모듈을 정했다.

ADR-0018(2026-10-01)로 가맹점주의 요청은 Store 서비스가 받고 Catalog는 `storeId`를 신뢰하는 내부 API를 제공하게 됐다. 이후 Store 서비스는 같은 문제를 반대 방향에서 정했다(2026-10-06, Store ADR-0001·0002·0004).

- 노출 판단에는 **매장 상태**가 들어간다. 개점 준비·휴업·폐점 매장의 상품은 손님에게 노출하지 않는다(Store 요구사항 4장 0단계). Catalog의 요구사항 3장에는 이 단계가 없다. Catalog가 판단하려면 매장 영업 상태 같은 사실을 복제해야 하고, 이것이 지금 [미정 사항](../architecture/README.md#미정-사항)의 "Store 정보 로컬 투영(`CatalogStore`)"이다.
- 매장 매니저의 진열·품절 변경은 매니저 지정으로 인가하는데, 매니저 지정은 Store의 데이터다.
- 손님 메뉴는 매장 단위로 만들어지고 매장 정보와 함께 보인다. Store가 제공하기로 했다.
- Store는 이미 매장 단위 상품 상태를 소유하는 설계를 채택했고, "Catalog 쪽 결정과 기존 매장 기능 정리는 Catalog가 자기 ADR로 다룬다"고 남겨 두었다. 그 후속이 비어 있어 두 서비스의 문서가 서로 반대 방향을 가리키고 있다.

부하테스트(#123)는 현재 구조의 비용도 보여 주었다. 로컬 참고값이고 한정 판매 분포는 가정에 기댄 값이다.

- 매장 상품 목록이 총 CPU의 대부분을 쓴다. 요청당 약 70ms이고 유효 옵션 조회는 약 9ms다. 목표 부하(목록 285 rps, 유효 옵션 180 rps)를 CPU 60% 이하로 받으려면 단순 산술로 목록만 약 20코어가 필요하다.
- 한정 판매 상품의 대상 매장 목록을 요청마다 읽는 것이 목록 요청당 CPU의 약 3분의 2다(#130). 이를 고쳐도 목표에는 약 14코어가 더 필요하다는 추정이다.
- 이 부하는 매장 수에 비례해 커지는 매장 요청(점주의 목록 조회와 변경, 손님의 메뉴 조회)에서 나온다.

## 결정

- **매장 단위의 상품 상태는 Store 서비스가 소유한다.** 매장별 진열 설정, 매장별 판매 가능 여부와 재고 이벤트 소비, 노출 판단, 손님 메뉴, 매장별 노출 현황, 판매 범위에서 빠진 매장의 설정 정리가 해당한다. Catalog는 이것들을 소유하지 않는다.
- **Catalog는 본사가 정의하는 것을 소유한다.** 상품, 옵션 그룹, 카테고리, 태그, 상품 그룹, 예약 변경, 그리고 **판매 범위**(대상 매장 목록 포함)다. 판매 범위는 매장에 판매를 허용하는 본사의 상품 정책이다.
- **Catalog는 판단에 필요한 상품 상태를 이벤트로 발행한다.** Store가 복제해 쓰는 값은 상품 ID, SKU, 상태, 판매 범위, 재고 추적 여부다.
  - 이벤트는 바뀐 부분이 아니라 **상품 상태 전체**를 담고, 상품별 순번과 발생 시각을 가진다. 순번은 같은 상품의 이벤트끼리 뒤에 일어난 것이 항상 크기만 하면 된다.
  - 종류는 등록됨, 활성화됨, 단종됨, 판매 범위 바뀜, 삭제됨이다. 종류는 기록용이고 Store는 담긴 상태로 복제본을 교체한다. 예약 적용으로 바뀐 경우도 같은 경로로 발행한다.
  - 상품 변경이 커밋되면 이벤트도 **반드시 나간다**(유실 없음). 같은 트랜잭션에 이벤트를 기록하는 아웃박스로 보장한다. 같은 상품의 이벤트는 순서대로 전달하고 중복 전달은 Store가 무시한다.
- **Catalog는 조회 API를 제공한다.** 모두 Store 서비스 계정(`catalog:store_agent`)이 부른다.
  - 상품 ID 목록의 기준 정보(SKU, 이름, 카테고리 ID, 이미지, 기준가, 재고 추적 여부, 표시용 시작가, 태그)를 한 번에
  - 카테고리 목록(대분류·소분류 구조와 **노출 순서**). 노출 순서는 Catalog에 새로 생기는 값이다.
  - 상품 하나의 유효 옵션 구성과 표시용 시작가(**매장과 관계없이**)
  - 복제본을 처음 채우거나 다시 맞출 전체 상품 상태 목록(이벤트와 같은 형태와 순번)
- **Catalog는 판매 범위의 대상 매장 확인을 Store에 요청한다.** 즉시 변경과 예약 등록 때 부르고, 예약 적용 때는 다시 부르지 않는다(Store 요구사항 7.2). 지금 임시 구현(`AlwaysExistingStoreAdapter`, `ConfiguredStoreDirectory`)을 Store 호출로 바꾼다.
- **Catalog의 매장 대상 API는 없앤다.** `/api/v1/internal/stores/{storeId}/**`(목록, 진열 순서, 숨김, 품절)와 `/api/v1/admin/stores/{storeId}/products`, 노출 현황 API는 Store가 맡는다. 본사 API(`/api/v1/admin/**`)의 나머지는 유지한다. 본사의 노출 현황 화면은 Catalog의 상품 목록과 Store의 매장별 집계를 본사 화면(또는 BFF)이 합친다.
- **이행은 단계적으로 한다.** 한 번에 바꾸지 않는다.
  1. Catalog에 이벤트 발행과 조회 API를 추가한다. 기존 매장 기능은 그대로 둔다.
  2. Store가 복제본과 판단을 구현하고 점주·손님 트래픽을 전환한다.
  3. 전환이 확인되면 Catalog에서 `store`·`exposure` 모듈, 두 테이블, 재고 이벤트 소비, 매장 대상 API를 제거한다.
  - 이행이 끝나기 전까지 현재 구조(요구사항 2·3장, 1.10)는 유효하다. 규칙의 원본이 Store 요구사항으로 옮겨 가는 시점은 3단계다.

## 검토한 대안

- **Catalog가 소유하고 매장 정보를 로컬 투영(`CatalogStore`)으로 받음**(지금 미정 사항의 안): 단종과 판매 범위 변경이 같은 트랜잭션에서 즉시 반영되고 이벤트 계약이 필요 없다. 하지만 노출 규칙에 영업 상태가 들어가면서 Catalog가 영업 상태, 매장 매니저 같은 매장 개념을 점점 더 알아야 하고 손님 메뉴까지 맡게 된다. 매니저의 모든 요청이 두 서비스를 거친다. Store가 같은 이유로 이미 기각했고, 부하 문제(매장 수에 비례하는 요청)도 그대로 Catalog에 남는다.
- **현재 구조를 유지하고 최적화**(#130 수정, 조회 캐시): 이벤트 계약과 이행 비용이 없다. 한정 판매 문제를 고치면 목록이 약 3배 가벼워지지만 목표 부하를 받으려면 여전히 목록 비용을 더 줄이거나 인스턴스를 늘려야 한다는 추정이다. 캐시는 원인을 가리는 방식이고 별도 설계 결정이 필요하다. 소유 경계 문제(매장 상태, 매니저, 손님 메뉴)는 해결하지 못한다.
- **Store가 화면 조립만 맡음**(ADR-0018의 현재 상태): 이미 채택된 구조다. 소유 경계와 부하를 바꾸지 않는다.
- **표시용 정보(이름, 가격, 옵션)까지 Store에 복제**: Store가 Catalog 장애와 무관하게 모든 화면을 보여 줄 수 있다. 하지만 상품 필드가 바뀔 때마다(예약 적용 포함) 이벤트가 필요하고, 옵션 그룹 하나를 바꾸면 연결된 상품 수백 개의 이벤트가 나간다. Store ADR-0002가 같은 이유로 기각했다.

## 결과

- **얻는 것**
  - 매장에 관한 사실과 매장별 상품 상태가 Store 한곳에 모인다. 영업 상태를 넣는 노출 규칙을 한 서비스가 판단한다.
  - Catalog는 본사의 상품 정의에 집중한다. Catalog가 받는 요청이 매장 수에 비례하는 매장 요청에서 상품 수 규모의 표시용 조회와 이벤트 발행으로 바뀐다. 표시용 정보는 매장과 무관하고 Store가 캐시하므로 호출량의 상한은 `상품 수 ÷ 캐시 시간` 정도다(캐시 시간은 Store가 운영하며 정한다).
  - 재고 이벤트 소비가 Catalog에서 빠진다.
  - #130(요청마다 한정 판매 상품의 대상 매장 전체를 읽음)의 대부분이 해소된다. 같은 비용이 "요청마다"에서 "상품 변경마다"(이벤트 페이로드)로 옮겨 가 훨씬 작아진다.
  - Catalog 장애와 무관하게 Store의 판단(노출, 진열·숨김·품절 변경, 재고 반영)이 계속된다.
- **감수하는 것**
  - 단종과 판매 범위 변경이 매장에 반영되기까지 지연이 생긴다(결과적 일관성). ADR-0003이 전제한 "같은 서비스 안의 즉시 반영"이 없어진다. 주문 시점의 검증은 주문·POS의 책임이다.
  - Catalog가 이벤트 발행(아웃박스, 상품별 순번, 등록·삭제 이벤트), 전체 상품 상태 목록 API, 카테고리 노출 순서, 상품 ID 배치 조회를 새로 갖춰야 한다. **메시징 기술이 아직 정해지지 않아** 이벤트 발행이 그 결정에 막혀 있다.
  - 판매 범위가 이벤트 페이로드가 된다. 한정 판매 상품은 대상 매장 목록 전체(수천 개 ID까지)를 상태 전체로 담고, 전체 상품 상태 목록 API의 응답도 그만큼 커진다.
  - 표시용 정보 조회가 실패하면 Store의 메뉴·매니저 화면 조회가 실패한다(손님 메뉴는 캐시로 완화).
  - 이행 중에는 두 구조가 함께 있다. 두 서비스의 계약(이벤트 형식, 순번, 조회 API)을 맞추는 비용이 든다.
  - 본사의 매장별 노출 현황은 한 서비스로 끝나지 않고 본사 화면이 합친다.
  - 이 결정이 근거로 삼은 부하 측정은 로컬 참고값이고 한정 판매의 실제 분포를 모른다. 분리의 근거는 소유 경계가 더 크고, 부하는 부가적인 이득이다.
- **후속 작업**
  - 메시징 기술을 정하는 ADR(이벤트 발행의 선결 조건)
  - 이벤트 형식과 조회 API를 Store와 맞춘다(Store 요구사항 7.1). 아웃박스와 순번의 설계를 정한다.
  - 이행 계획(단계, 전환 시점, 롤백)을 문서로 쓴다. 운영 데이터가 있다면 `store_display_settings`·`store_product_availabilities`를 Store로 옮기는 절차를 정한다.
  - 문서 개정은 요구사항 → 시나리오 → 도메인 모델 → ERD 순서로 한다. 요구사항 2·3장과 1.10은 Store로 이동하고 비기능 요구사항(4장)의 부하 모델은 조회 API, 이벤트 발행, 본사 API, 예약 배치 기준으로 다시 쓴다(#122).
  - 이슈 #130은 소유 이전 이후에도 남는 부분(표시용 조회, 이벤트 페이로드)만 다시 정리한다. 이전 완료 전에 현재 구조의 목록을 고칠지는 이행 일정을 보고 정한다.
  - 부하테스트 도구(`loadtest/`)의 매장 요청 시나리오와 시드는 Store로 옮기고, Catalog는 새 계약 기준으로 다시 짠다(#123).
