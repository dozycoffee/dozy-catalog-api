# ADR-0016: SKU는 시스템이 전용 시퀀스로 발급하고 의미를 담지 않는다

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: 이슈 #63, [요구사항](../requirements.md) 1.2, [ERD](../erd.md#products--상품-마스터)

## 맥락

요구사항 1.2는 "상품에는 상품 ID와 별도로 SKU가 부여되며, 외부 시스템(POS, 재고관리 서비스 등) 연동 시 식별 키로 사용된다"고만 정했다. 누가 어떤 형식으로 만드는지는 정하지 않아 지금까지 `sku`를 NULL로 두고 있었다. 상품 등록 유스케이스를 만들면서 정해야 했다.

SKU는 한 번 밖으로 나가면 POS·재고관리 서비스·거래 이력에 박히고, 우리가 마음대로 바꿀 수 없다. 되돌리기 비싼 외부 계약이다.

## 결정

- **시스템이 등록 시점에 부여한다.** 본사관리자가 입력하지 않는다.
- **형식은 `DZ-00000123`이다.** 고정 접두사 `DZ-`와 8자리 일련번호다. 대문자 영숫자와 하이픈만 쓰고 자릿수를 고정해, POS 화면·라벨·CSV에서 깨지거나 정렬이 흐트러지지 않게 한다.
- **상품 ID와 분리된 전용 시퀀스**(`product_sku_seq`, V4)에서 번호를 받는다.
- **의미를 담지 않는다.** 카테고리·상품명 같은 분류나 속성을 코드에 넣지 않는다.
- 형식은 `SkuGenerator` 구현 한 곳에서만 만든다.
- 한 번 쓴 SKU는 다시 쓰지 않는다(시퀀스라 자연히 지켜진다). 상품을 삭제해도 그 번호는 재사용되지 않는다.
- **바코드(GTIN/EAN)는 SKU와 다른 개념이라 넣지 않는다.** 외부에서 사입한 MD를 다루게 되면 별도 컬럼으로 추가한다.

## 검토한 대안

- **의미를 담는 코드(`BV-COF-AMR-001`)**: 사람이 코드만 보고 무엇인지 알 수 있다. 하지만 우리 요구사항에서 소분류는 다른 대분류로 이동할 수 있고 이름도 바꿀 수 있으며(1.6), 상품명도 수정 가능하다(1.3). 이미 외부에 나간 SKU는 따라 바꿀 수 없으므로 코드와 실제가 곧 어긋난다.
- **재고 추적 여부를 접두사로(`MD-` / `MN-`)**: 이 값은 등록 후 바뀌지 않아 거짓말이 되지는 않는다. 발주·물류에서 구분이 편하다는 이점이 있지만, 그 구분은 조회하면 나오므로 접두사를 하나로 두어 단순하게 갔다. 필요해지면 접두사 규칙만 바꾸면 되고 이미 발급된 SKU는 그대로 둔다.
- **상품 ID를 그대로 사용**: 시퀀스가 필요 없어 가장 단순하다. 하지만 내부 식별자가 외부 시스템에 새고, 상품 ID 체계가 바뀌면 SKU까지 흔들린다.
- **본사관리자가 직접 입력**: 외부 코드 체계를 그대로 따라야 하는 경우에 필요하다. 지금은 그런 요구가 없고, 사람이 입력하면 중복·오타·형식 불일치를 계속 다뤄야 한다.

## 결과

- **얻는 것**: 속성이 바뀌어도 SKU가 틀리지 않는다. 등록만 하면 외부 연동 키가 항상 있다. 형식이 한곳에 있어 바꾸기 쉽다.
- **감수하는 것**: 코드만 보고는 무슨 상품인지 알 수 없다. 조회 화면이 SKU로 상품을 찾을 수 있어야 한다.
- **후속 작업**: 외부 사입 MD를 다루게 되면 바코드 컬럼을 별도로 추가한다. 본사관리자가 SKU로 상품을 찾는 조회가 필요해지면 `products.sku`의 UNIQUE 인덱스를 그대로 쓴다.
