# ADR-0019: 실행 이미지는 Dockerfile로 만들고, main의 버전 태그로 GitHub Container Registry에 배포한다

- **상태**: 채택
- **날짜**: 2026-10-06
- **관련**: #116, [README 배포](../../README.md#배포), dozy-auth의 라이브러리 배포 방식(`publish.yml`)

## 맥락

Catalog를 컨테이너 이미지로 배포해야 한다. 조직에서 이미지를 내는 첫 서비스라, 여기서 정한 방식을 다른 서비스(WMS, Auth 서버, Store)가 따라갈 가능성이 크다.

정해야 할 것은 세 가지였다.
- 이미지를 무엇으로 만드는가
- 언제, 어디로 올리는가
- 버전을 어떻게 붙이는가

빌드에는 GitHub Packages 인증이 필요하다(dozy-auth 라이브러리).

## 결정

- **이미지는 Dockerfile로 만든다.**
  - 베이스는 `eclipse-temurin:21-jre`다.
  - 실행 jar를 `jarmode=tools extract --layers`로 풀어 의존성·로더·스냅샷·앱 코드 레이어로 나눈다.
  - root가 아닌 사용자(uid 1001)로 실행한다.
  - 힙은 컨테이너 메모리 한도의 75%(`MaxRAMPercentage`)로 둔다.
- **jar는 이미지 밖(CI의 Gradle)에서 빌드하고, Dockerfile은 만들어진 jar만 받는다.** GitHub Packages 인증을 이미지 빌드 안으로 넘기지 않는다.
- **배포는 main 커밋의 `v{major}.{minor}.{patch}` 태그로 한다.**
  - 워크플로가 태그 커밋이 main에 있는지 확인하고, 빌드·테스트를 다시 돌린다.
  - 이미지를 `ghcr.io/dozycoffee/dozy-catalog-api`에 올리고 GitHub Release를 만든다. dozy-auth의 라이브러리 배포와 같은 흐름이다.
- **이미지 태그는 버전(`0.1.0`)과 커밋(`sha-…`)만 둔다.** `latest`는 어떤 버전이 떠 있는지 모호하게 만들어 두지 않는다.
- **버전은 SemVer를 따르고 `v0.1.0`부터 시작한다.**
  - 0.x 동안 API 호환이 깨지는 변경은 minor를 올린다.
  - 1.0.0은 운영에서 API 계약을 지키기로 할 때 붙인다.
  - API 경로의 `/api/v1`은 API 계약의 버전이라 이미지 버전과 따로 간다.

## 검토한 대안

- **Spring Boot `bootBuildImage`(Cloud Native Buildpacks)**
  - 좋은 점: Dockerfile 없이 레이어 분리, 컨테이너 메모리에 맞춘 JVM 설정, root 아닌 사용자, 베이스 이미지 갱신을 알아서 해 준다.
  - 택하지 않은 이유:
    - 무엇이 들어가는지 잘 보이지 않는다.
    - 바꾸려면 Buildpacks의 `BP_*` 설정을 알아야 한다.
    - 첫 빌드에 큰 builder 이미지를 받는다.
    - 다른 서비스가 가져다 쓸 틀로는 누구나 읽고 고칠 수 있는 Dockerfile이 낫다.
- **이미지 안에서 Gradle로 빌드(멀티 스테이지)**: CI 환경과 무관하게 같은 이미지를 만들 수 있다. 하지만 GitHub Packages 토큰을 빌드 비밀로 넘겨야 하고, Gradle 캐시를 이미지 빌드에서 따로 관리해야 한다.
- **main에 머지할 때마다 배포**: 배포 단위가 커밋마다 생겨 버전과 변경 내역을 묶기 어렵다. 라이브러리처럼 의도한 시점에 태그로 낸다.

## 결과

- **얻는 것**
  - 이미지 구성이 파일 하나에 드러나고, 다른 서비스가 그대로 가져다 쓸 수 있다.
  - 배포가 리뷰를 거친 main의 커밋으로만 일어나고, 버전·이미지·릴리스 노트가 하나로 묶인다.
  - 코드만 바뀌면 앱 레이어(수 MB)만 다시 올라간다.
- **감수하는 것**
  - 베이스 이미지(JRE) 보안 패치를 직접 따라가야 한다. 베이스 태그를 올린 뒤 새 버전을 낸다.
  - JVM 옵션과 실행 사용자 같은 기본값을 직접 관리한다.
  - 이미지를 빌드하기 전에 jar가 있어야 한다(`./gradlew bootJar`).
- **후속 작업**
  - 패키지 공개 범위와 배포 환경의 pull 권한을 정한다.
  - 배포 대상 환경이 정해지면 플랫폼(지금은 `linux/amd64`)과 마이그레이션 실행 시점을 다시 본다.
