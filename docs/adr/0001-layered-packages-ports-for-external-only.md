# ADR-0001: 레이어 우선 패키지 구조를 쓰고, 포트는 외부 시스템 연동에만 둔다

- **상태**: 일부 대체됨 (포트 배치 → ADR-0012)
- **날짜**: 2026-08-17 (소급 작성)
- **관련**: PR #2, [패키지 구조](../architecture/package-structure.md)

## 맥락

Catalog 서비스는 그 자체로 하나의 BC이자 배포 단위다. 안에는 Product, OptionGroup, Category, Tag, ProductGroup, ScheduledChange, 매장 설정 등 여러 애그리거트가 있고, 바깥으로는 Store BC, 재고관리 서비스, POS·정산과 연동한다. 패키지를 어떻게 나누고, 어디에 인터페이스(포트)를 둘지 정해야 했다.

## 결정

- 최상위 패키지는 레이어(`domain` / `application` / `infrastructure` / `presentation`)로 나누고, 그 아래를 애그리거트별로 나눈다.
- 의존 방향은 `presentation → application → domain ← infrastructure`다. domain은 프레임워크를 모른다.
- 포트 인터페이스는 **실제로 네트워크 경계를 넘는 외부 시스템 연동**(Store BC 조회, 재고 이벤트 구독, POS·정산 이벤트 발행)에만 둔다. 같은 서비스 안의 애그리거트끼리는 포트로 감싸지 않고 직접 호출하거나 도메인 이벤트로 협력한다.

## 검토한 대안

- **애그리거트 우선 패키지(각 애그리거트 안에 레이어)**: 애그리거트별 독립성은 높지만, 한 BC 안에서 레이어 규칙(의존 방향)이 애그리거트마다 흩어져 지키기 어렵다.
- **애그리거트마다 포트·어댑터로 격리(헥사고날을 애그리거트 단위로)**: 같은 배포 단위·같은 트랜잭션 안에서 인터페이스만 늘고 얻는 격리가 없다.

## 결과

- **얻는 것**: 레이어 규칙이 한눈에 보이고, 외부 연동 지점이 포트로 명확히 모인다.
- **감수하는 것**: 애그리거트를 다른 서비스로 떼어 낼 때는 레이어마다 흩어진 코드를 모아야 한다.
- **후속 작업**: 서브패키지 기준(파일 수, 역할 종류)과 전체 트리는 [패키지 구조](../architecture/package-structure.md)에서 관리한다.
