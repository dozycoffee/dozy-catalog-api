# ADR-0007: 사용자가 일으킬 수 있는 규칙 위반은 DomainException, 호출 코드 오류는 require/check

- **상태**: 채택
- **날짜**: 2026-09-19 (소급 작성)
- **관련**: PR #33, #35, #36, [예외 구조](../architecture/exception.md), ADR-0002

## 맥락

도메인 서비스가 생기면서, 사용자 요청이 아니라 호출하는 코드(application)의 실수로만 생기는 오류가 나타났다. 예를 들어 판매 범위 정리 계산에 다른 상품의 설정이 섞여 들어오거나, 유효 옵션 구성 계산에 넘긴 옵션 그룹이 상품의 연결과 다른 경우다. 이런 오류까지 `DomainException`으로 던지면 4xx로 응답하게 된다.

## 결정

| 상황 | 쓰는 것 | 결과 |
|---|---|---|
| 사용자 요청으로 생길 수 있는 규칙 위반 | `DomainException` 서브클래스 | `ErrorType`에 따라 4xx와 `ErrorResponse` |
| 사용자가 일으킬 수 없고 호출 코드가 잘못됐을 때만 생기는 상황 | Kotlin 표준 함수 `require`(인자) / `check`(상태) | 처리되지 않은 예외로 500과 error 로그 |

어느 쪽인지 애매하면 `DomainException`을 쓴다.

## 검토한 대안

- **호출 코드 오류도 `DomainException`으로(예: 404)**: 버그가 4xx로 보고되어 모니터링에서 숨는다. 클라이언트는 고칠 수 없는 오류 코드를 받는다. 절대 오지 않을 코드가 오류 코드 목록(API 계약)에 섞인다.
- **`DomainException`에 `ErrorType.INTERNAL`을 추가해 500으로 매핑**: 예외 계층은 하나로 통일되지만, 내부 오류 코드가 클라이언트 계약에 섞이지 않게 따로 관리해야 한다.

## 결과

- **얻는 것**: 버그는 500과 error 로그로 드러나고, 오류 코드 목록에는 클라이언트가 대응할 수 있는 코드만 남는다.
- **감수하는 것**: 처리되지 않은 예외는 지금 Spring 기본 오류 형식으로 나가서 `ErrorResponse`와 형식이 다르다. HTTP가 아닌 경로(이벤트 핸들러, 배치)에서는 어느 예외든 500으로 바뀌지 않고 호출자에게 그대로 올라간다.
- **후속 작업**: 나머지 예외를 모두 잡는 핸들러로 응답 형식을 통일하는 일과, 이벤트 핸들러·배치의 예외 격리 방식은 [미정 사항](../architecture/README.md#미정-사항)에 있다.
