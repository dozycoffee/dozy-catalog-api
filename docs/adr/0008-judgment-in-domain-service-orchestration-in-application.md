# ADR-0008: 판단은 도메인 서비스, 오케스트레이션과 트랜잭션 경계는 application

- **상태**: 채택
- **날짜**: 2026-09-19 (소급 작성)
- **관련**: 이슈 #38, PR #33, #35, #40, [도메인 모델](../domain-model.md), [요구사항](../requirements.md) 1.9

## 맥락

여러 애그리거트를 함께 봐야 하는 규칙(요구사항 1.5, 1.9)을 도메인 서비스로 옮기면서 두 가지 형태가 섞였다.
- `StoreScopeCleanupPolicy`는 삭제할 ID 목록만 돌려주고, 삭제는 호출자가 한다.
- `OptionListReplacer`는 판단에 더해 OptionGroup과 연결 Product들을 직접 바꿨다.

후자처럼 하면 "한 트랜잭션에서 여러 애그리거트를 바꾼다"는 결정이 도메인 안에 숨는다. 이 결정은 트랜잭션을 여는 쪽에서 드러나야 한다. 반대로 판단까지 application으로 올리면 규칙을 테스트하기 어렵고, 즉시 변경과 예약 적용에서 같은 규칙이 중복된다.

## 결정

- **도메인 서비스**는 한 애그리거트에 속하지 않는 비즈니스 판단만 하고 결과를 돌려준다. 어떤 애그리거트도 바꾸지 않으며 저장소를 모른다. 예: `EffectiveOptionResolver`, `StoreScopeCleanupPolicy`, `OptionReplacementPolicy`.
- **애그리거트**는 자기 상태를 스스로 바꾼다.
- **application 서비스**는 조회, 잠금, 도메인 서비스 호출, 각 애그리거트에 변경 요청, 저장, 이벤트 발행을 진행하고 트랜잭션 경계를 정한다.
- **옵션 목록 교체는 OptionGroup과 연결 Product들을 한 트랜잭션에서 바꾼다.** 요구사항 1.9("하나라도 0개가 되면 변경 전체 거부") 때문에 검증과 교체가 원자적이어야 한다. 흐름은 옵션 그룹 잠금 → 연결 상품 전체 조회 → `OptionReplacementPolicy.check()` → `OptionGroup.replaceOptions()` → 상품마다 `Product.removeOverrides()` → 저장이다. 즉시 교체와 예약 스냅샷 적용이 같은 흐름을 쓴다.

## 검토한 대안

- **여러 애그리거트가 얽힌 로직을 모두 application 서비스에**: 판단 규칙이 유스케이스마다 흩어지고, 인프라 없이 테스트하기 어렵다.
- **도메인 서비스가 판단과 변경을 모두(기존 `OptionListReplacer`)**: 트랜잭션 경계 결정이 도메인에 숨는다. 호출 순서에 의존하는 메서드가 생긴다(교체가 먼저 반영돼야 동작하던 `removeOverridesOfMissingOptions`).
- **사라진 옵션 키의 예외 정리를 이벤트로 나중에 처리(결과적 일관성)**: 한 트랜잭션에 한 애그리거트 원칙은 지킬 수 있다. 하지만 잠깐이라도 존재하지 않는 키를 가리키는 예외가 남고, 1.9의 전체 거부 규칙은 어차피 동기 판단이 필요하다.

## 결과

- **얻는 것**: 규칙은 도메인 서비스 단위로 테스트된다. 트랜잭션 경계 결정은 application 코드에서 보인다.
- **감수하는 것**: 옵션 목록 교체는 "한 트랜잭션에 애그리거트 하나" 원칙의 예외다. 같은 BC, 같은 DB라서 감당할 수 있다고 판단했다.
- **후속 작업**: application 계층을 만들 때 이 흐름대로 구현한다.
