# ADR-0022: 매장과 무관한 읽기 전용 참조 데이터는 토큰 없이 읽는 공개 경로로 제공한다

- **상태**: 채택
- **날짜**: 2026-10-15
- **관련**: 이슈 #147, [ADR-0018](0018-partner-requests-through-store-service.md)(일부 대체), [ADR-0020](0020-store-owns-store-product-state.md), [API 명세](../api/README.md#경로와-인가), [공개 참조 데이터](../api/public.md), 요구사항 1.6

## 맥락

ADR-0018은 점주·손님의 요청을 Store 서비스가 받고, Catalog는 Store 서비스만 부르는 `/internal/**`로 제공하게 했다. 근거는 두 가지였다. 점주 토큰(realm `partner`, `aud: ["store"]`)은 Catalog에 들어올 수 없고, "이 요청자가 이 매장의 점주인가"는 Store만 판단할 수 있다.

카테고리 트리는 매장과 무관하다. 모든 매장과 채널에서 같은 대분류·소분류와 노출 순서이고(요구사항 1.6), 상품이 `categoryId`를 담아 이미 채널에 나가므로 민감한 정보도 아니다. 매장 소유 확인이 필요 없어 ADR-0018의 근거가 해당하지 않는다. 그런데도 카테고리를 받으려면 Catalog → Store(10분 캐시) → 채널을 거친다. Store는 값을 걸러내거나 가공하지 않고 전달만 하므로, 카테고리 응답이 바뀔 때마다 Store 변경과 배포가 함께 필요하고 순서 변경은 Store 캐시만큼 늦게 반영된다.

## 결정

- **매장과 무관한 읽기 전용 참조 데이터는 `/api/v1/public/**`로 토큰 없이 제공한다.** `GET`만 열고, 다른 메서드는 인증을 요구한다.
- **지금 공개하는 것은 카테고리 트리뿐이다.** 응답은 `/internal/categories`와 같다. 태그는 상품 응답에 이름이 담기고, 상품 그룹은 본사 내부용(요구사항 1.8)이라 열지 않는다.
- **공개 범위를 넓히려면 새 ADR을 쓴다.** 조건은 매장과 무관하고, 읽기 전용이며, 본사 내부 정보를 담지 않는 것이다.
- **응답에 `Cache-Control: public, max-age=600`을 붙인다.** 채널과 중간 캐시가 흡수하므로 공개해도 Catalog의 부하가 채널 수에 비례하지 않는다. 순서 변경의 반영 지연은 기존 Store 캐시와 같은 10분이다.
- 상품, 매장별 상태, 옵션 같은 나머지는 그대로 Store 서비스를 거친다. ADR-0018의 경로 구분(`/admin/**`, `/internal/**`)은 유지하고 공개 경로를 하나 더한다.
- `/internal/categories`는 Store가 호출을 걷어낼 때까지 남긴다.

## 검토한 대안

- **현행 유지(Store가 중계)**: 변경이 없다. 하지만 값을 전달만 하는 서비스를 거쳐 응답 변경마다 두 서비스가 함께 바뀌고 반영이 늦다.
- **partner 토큰의 `aud`에 `catalog`를 추가**: 채널이 토큰으로 직접 부를 수 있다. 하지만 Auth의 결정(`aud` 고정, 점주에게 role을 부여하지 않음)을 바꿔야 하고, 로그인 전 화면에는 쓸 수 없다. 카테고리에는 신원이 필요 없어 얻는 것이 없다.
- **카테고리를 상품 응답에 이름까지 넣기**: 채널이 따로 받지 않아도 된다. 하지만 "리소스는 자기 데이터만 담고 다른 리소스는 ID로 가리킨다"는 원칙([API 명세](../api/README.md#설계-원칙))과 어긋나고, 카테고리 이름·순서 변경이 모든 상품 이벤트와 캐시에 번진다.

## 결과

- **얻는 것**
  - 카테고리 변경이 Store 변경 없이 채널에 닿는다.
  - 카테고리 읽기 경로가 하나 줄어 운영할 곳이 줄고, 순서 변경의 반영 경로가 단순해진다.
- **감수하는 것**
  - 인증 없는 경로가 생긴다. 응답에 필드를 더할 때마다 공개해도 되는지 확인해야 한다. 헬스 체크와 지표 외에 처음으로 사업 데이터가 공개된다.
  - 채널이 Catalog 주소를 알고 직접 부른다. 호출 대상이 Store와 Catalog 둘이 된다.
  - 공개 경로는 호출자를 알 수 없어 호출량을 구분해 막기 어렵다. 캐시 헤더와 앞단(게이트웨이·CDN)의 제한에 기댄다.
- **후속 작업**
  - Store 담당과 `/internal/categories` 호출을 걷어내는 시점을 정하고, 걷어내면 그 경로와 API 문서 항목을 지운다.
  - 공개 경로의 CORS 출처(`CATALOG_PUBLIC_CORS_ALLOWED_ORIGINS`)에 웹 채널의 주소를 정해 배포 환경에 넣는다.
  - 배포 환경의 게이트웨이에서 `/api/v1/public/**`의 노출과 호출 제한을 정한다.
