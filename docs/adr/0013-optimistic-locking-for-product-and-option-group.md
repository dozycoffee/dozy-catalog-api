# ADR-0013: 낙관적 잠금은 Product와 OptionGroup에만 쓰고, 충돌은 사람이 다시 판단한다

- **상태**: 채택
- **날짜**: 2026-09-19
- **관련**: 이슈 #47, ADR-0010(동시 수정 부분 대체), [ERD 동시성 처리](../erd.md#동시성-처리), [영속성 규칙](../architecture/persistence.md)

## 맥락

ADR-0010은 모든 애그리거트 루트 테이블에 `version`을 두기로 했다. Repository를 구현하면서 애그리거트마다 동시 수정이 어떤 모양인지 다시 보니 서로 달랐다.
- Product와 OptionGroup은 관리자가 화면에서 오래 보다가 전체를 덮어쓰는 수정(PUT, 예외 지정)이 있고, 같은 대상을 시스템(00시 예약 적용, 옵션 목록 교체 때 예외 정리)도 바꾼다. 오래된 화면으로 저장하면 다른 변경을 조용히 지운다.
- 다른 애그리거트의 경합은 이미 다른 방식으로 막고 있다. 예약은 행 잠금과 상태 조건 UPDATE, 매장 진열 설정은 바뀐 필드만 UPDATE, 판매 가능 여부는 `last_event_at` 조건부 upsert, 카테고리 이동은 부모 행 잠금이다. 카테고리·태그·상품 그룹의 이름 변경 충돌은 피해가 작다.

쓰이지 않는 `version` 컬럼이 남으면 "여기도 낙관적 잠금이 있다"는 오해를 부른다.

## 결정

- **낙관적 잠금은 Product와 OptionGroup에만 쓴다.** 두 애그리거트는 `VersionedAggregateRoot`를 상속한다. 나머지 테이블의 `version`은 V2 마이그레이션에서 제거한다.
- **검사는 두 겹으로 한다.**
  - application이 화면에서 받은 버전으로 `checkVersion(expected)`를 호출한다. 오래된 화면이면 바로 거부한다.
  - Repository는 `UPDATE … WHERE id = ? AND version = ?`로 저장하고 성공하면 `version`을 1 올린다. 바뀐 행이 0개면 그 사이 다른 트랜잭션이 저장한 것이므로 충돌이다.
- **충돌은 `VersionConflictException`(`SharedErrorCode.VERSION_CONFLICT`, `CONFLICT`, 409)이다.** 알 수 있으면 현재 버전을 함께 담는다. `ConcurrentModificationException`은 Kotlin·JDK 표준 예외와 이름이 겹쳐 쓰지 않는다.
- **사람의 요청은 자동으로 재시도하지 않는다.** 화면이 최신 값을 다시 불러와 관리자가 다시 판단한다.
- **버전을 요구하는 요청은 전체 교체(PUT)와 상품별 예외 지정이다.** 상태 액션(활성화·단종)과 예약 등록은 요구하지 않는다. 상태 전이는 Product 행 잠금으로 막고, 예약은 적용 시점의 값에 대해 규칙을 다시 검증한다. API 형식은 API 작업 때 정한다.
- 시스템이 바꾸는 경로(예약 적용, 옵션 교체 때 예외 정리)는 행 잠금 뒤 최신 상태로 바꾸므로 `checkVersion`을 부르지 않는다. 저장할 때 버전은 올려서, 그 사이 화면을 보던 관리자의 저장이 충돌로 드러나게 한다.

## 검토한 대안

- **모든 애그리거트 루트에 낙관적 잠금(ADR-0010)**: 경합의 모양이 다른 곳까지 한 방식으로 묶는다. 예를 들어 재고 이벤트는 순서 역전을 `last_event_at`으로 걸러야 하고, 버전 충돌로 거부하면 오히려 최신 이벤트를 잃는다.
- **비관적 잠금만 사용**: 트랜잭션 안의 경합은 막지만, 사람이 화면을 보는 동안 다른 변경이 들어온 경우(트랜잭션 밖의 경합)는 막지 못한다.
- **충돌 시 서버가 자동 재시도하거나 마지막 저장이 이기게 둠**: 관리자가 보지 못한 변경을 덮어쓴다.

## 결과

- **얻는 것**: 관리자가 오래된 화면으로 다른 변경을 덮어쓰지 못한다. 잠금 방식이 애그리거트의 경합 모양에 맞는다.
- **감수하는 것**: 충돌하면 관리자가 다시 입력해야 한다. 잠금 방식이 애그리거트마다 달라 [ERD 동시성 처리](../erd.md#동시성-처리) 표를 함께 봐야 한다.
- **후속 작업**: Product·OptionGroup Repository(#48, #51)에서 버전 조건 저장을 구현한다. API 작업에서 요청의 버전 전달 방식과 409 응답 형식을 정한다.
