# ADR-0015: 최상위 패키지를 도메인 모듈로 두고, 그 안에서 레이어를 나눈다

- **상태**: 채택
- **날짜**: 2026-09-20
- **관련**: 이슈 #59, ADR-0001(대체), ADR-0012·ADR-0013(규칙은 유지), [패키지 구조](../architecture/package-structure.md)

## 맥락

ADR-0001은 최상위를 레이어(`domain` / `application` / `infrastructure` / `presentation`)로 두고 그 아래를 애그리거트로 나눴다. 그때는 코드가 domain 레이어뿐이라 문제가 드러나지 않았다.

영속성까지 구현하고 나니 한 애그리거트를 고치는 데 최상위 패키지 네 곳을 오가게 됐다. 상품에 필드 하나를 더하면 `domain/product`, `infrastructure/persistence/product`(Table과 Repository), 그리고 3단계에서 생길 유스케이스와 컨트롤러까지 흩어진 자리를 모두 고쳐야 한다. 반대로 한 폴더 안에는 서로 거의 엮이지 않는 파일이 모여 있다. **함께 바뀌는 것이 떨어져 있고, 함께 바뀌지 않는 것이 붙어 있다.** 3단계에서 유스케이스·커맨드·컨트롤러·DTO가 들어오면 거리는 더 벌어진다.

Evans의 Module 패턴은 모듈을 기술 역할이 아니라 도메인 개념으로 묶고 그 이름도 유비쿼터스 언어의 일부로 보라고 한다. 지금의 최상위 이름은 전부 기술 역할이다.

## 결정

- **최상위 패키지는 도메인 모듈이고, 모듈 안에서 레이어를 나눈다.** 모듈은 요구사항의 장 구분을 따른다.
  - `product`(1장 본사 상품관리), `store`(2·3장 가맹점 상품관리), `schedule`(1.4 예약 변경), `exposure`(1.10 노출 현황 조회)
- **애그리거트는 모듈 안의 패키지다.** 애그리거트는 트랜잭션 경계이지 모듈 경계가 아니다.
- **모듈 밖에는 `core`(도메인 공통 타입)와 `common`(기술 공통)만 둔다.** 둘 다 모듈을 참조하지 않는다.
- **모듈 간 의존은 단방향이다.** `store → product`, `schedule → product`, `exposure → product, store`.
- **계층별 참조 범위**: `domain`은 다른 모듈의 ID 타입만, `application`은 다른 모듈의 도메인 모델을 읽기만, `infrastructure`는 모듈 의존과 같은 방향이면 허용, `presentation`은 자기 모듈만.
- **다른 모듈의 애그리거트는 바꾸지 않는다.** 바꿔야 하면 그 모듈의 유스케이스를 호출하거나 이벤트를 발행한다.
- 모듈 안의 의존 방향, 애그리거트 간 ID 참조, 판단을 application 정책에 두는 규칙(ADR-0012), 낙관적 잠금(ADR-0013)은 그대로다. **위치만 바뀐다.**

## 검토한 대안

- **레이어 우선 유지(ADR-0001)**: 계층 규칙이 한눈에 보이는 장점이 있지만, 위에 적은 응집도 문제가 그대로 남는다. 코드가 커질수록 나빠진다.
- **애그리거트마다 모듈(8개)**: 함께 바뀌는 것이 가장 가까워지지만, 경계를 잘못된 곳에 긋는다. Product와 OptionGroup은 옵션 목록 교체에서 한 트랜잭션으로 함께 바뀌고(요구사항 1.9), 유효 옵션 구성 계산과 교체 검증이 양쪽을 함께 본다. 모듈로 가르면 둘 사이에 양방향 의존이 생긴다. 노출 판단, 판매 범위 정리, 예약 적용, 노출 현황 조회까지 더하면 모듈 간 의존이 촘촘해진다.
- **`catalog`이라는 모듈 이름**: base package(`com.dozycoffee.catalog`)가 이미 BC 이름이라 `catalog.catalog`가 된다. 모듈 이름은 BC 안에서 무엇을 맡는지를 말해야 한다.
- **`shared` + `common`**: 두 이름이 거의 같은 뜻이라 무엇을 어디에 둘지 매번 헷갈린다. `core`(도메인) / `common`(기술)로 나눴다.

## 결과

- **얻는 것**
  - 함께 바뀌는 코드가 모듈 하나 안에 모인다. 3단계에서 늘어나는 유스케이스·컨트롤러도 같은 자리에 들어간다.
  - 모듈 간 의존이 단방향으로 드러난다. 나중에 서비스를 쪼갠다면 자를 선이 이 경계다.
  - 모듈 이름이 요구사항의 장 구분과 1:1이라 문서와 코드가 같은 말을 쓴다.
- **감수하는 것**
  - `product` 모듈이 크다(애그리거트 5개). 함께 바뀌는 사이라 의도적으로 묶었다.
  - 모듈 안에서는 여전히 레이어를 오간다. 범위가 모듈 안으로 좁아질 뿐이다.
  - 계층 규칙이 모듈마다 반복되므로 리뷰에서 지켜야 한다. 의존 규칙을 테스트로 강제하는 일의 값어치가 커졌다([미정 사항](../architecture/README.md#미정-사항)).
  - 구조 관련 ADR이 0001 → 0012 → 0015로 짧은 기간에 세 번 바뀌었다. 0001은 코드가 domain뿐일 때의 판단이었고, 영속성까지 구현한 뒤에야 응집도 문제가 코드로 드러났다.
- **후속 작업**: 3단계(application 서비스) 이슈는 이 구조를 전제로 작성한다.
