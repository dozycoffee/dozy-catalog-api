# ADR-0017: API는 리소스 단위로 설계하고, 호출자별로 경로를 나눈다

- **상태**: 채택
- **날짜**: 2026-09-21
- **관련**: [API 명세](../api/README.md), ADR-0013(낙관적 잠금), ADR-0015(모듈 구조)

## 맥락

REST API를 구현하기 전에 외부 계약인 API 명세를 먼저 정해야 했다. 처음 초안은 화면을 기준으로 응답을 짰다. 상품 응답에 카테고리 이름·태그 이름을 넣고, 매장 상품 목록에 상품명·이미지·가격을 넣고, 노출 현황에 상품명을 넣었다. 이렇게 하면 화면이 바뀔 때마다 백엔드 응답도 바뀌고, 같은 정보를 여러 응답이 겹쳐 담게 된다. 조합 응답은 모듈 경계도 넘는다. 예를 들어 상품 조회에 대기 예약을 합치면 `product`가 `schedule`을 알아야 한다.

호출자는 본사관리자와 가맹점주 둘이고, 볼 수 있는 범위가 다르다. 상품 그룹은 본사 내부용이라 점주에게 보여 주면 안 되고(요구사항 1.8), 점주는 자기 매장에서 판매하는 상품만 다루면 된다. 인증 방식은 아직 정해지지 않았다.

## 결정

- **API는 화면이 아니라 리소스 단위로 설계한다.** 리소스는 자기 데이터만 담고 다른 리소스는 ID로만 가리킨다. 한 화면에 필요한 정보는 클라이언트가 여러 API를 불러 조립한다.
- **조립할 수 있도록 목록 API는 `ids`로 여러 건을 한 번에 조회할 수 있게 한다.**
- **업무 규칙이 들어간 계산은 백엔드가 리소스로 제공한다.** 노출 판단, 유효 옵션 구성과 표시용 시작가, 노출 매장 수가 그렇다. 클라이언트가 조립하는 것은 표시를 위한 결합까지다.
- **경로는 호출자별로 나눈다.**
  - `/api/v1/admin/**`: 본사관리자. 본사의 모든 API.
  - `/api/v1/stores/{storeId}/**`: 그 매장의 가맹점주. 매장별 상품 상태.
  - `/api/v1/products/**`, `/categories`, `/tags`: 가맹점주가 판매하는 상품의 조회. 본사 내부 정보를 뺀 응답.
- 같은 리소스를 두 경로에서 조회하면 같은 조회 로직을 쓰고, 조회 범위와 응답 필드만 다르다.
- **낙관적 잠금 버전은 `If-Match` 헤더로 받는다.** 버전이 필요한 요청에 본문 없는 `DELETE`(연결 해제, 예외 해제)가 있어 본문 필드로는 일관되게 받을 수 없다.

## 검토한 대안

- **화면 기준 조합 응답**: 클라이언트 호출 수가 적다. 하지만 화면이 바뀔 때마다 백엔드가 바뀌고, 같은 정보를 여러 응답이 겹쳐 담으며, 조합이 모듈 경계를 넘는다.
- **리소스 경로 하나에 역할별 인가**: `/products`를 본사와 점주가 함께 쓰고, 역할에 따라 조회 범위와 응답 필드(`groupIds` 등)를 바꾼다. 경로는 적지만 같은 경로의 응답이 요청자에 따라 달라지고, 인가 규칙을 엔드포인트마다 따져야 해 빠뜨리기 쉽다. 게이트웨이에서 본사 API만 따로 막을 수도 없다.
- **점주용 매장 상품 목록에 상품 정보를 함께 담음**: 점주 범위가 정확히 제한되지만 매장 리소스가 상품 정보를 겹쳐 담는다.
- **버전을 요청 본문으로 받음**: 클라이언트 구현은 쉽지만 `DELETE`에서 쓸 수 없다.

## 결과

- **얻는 것**
  - 화면이 바뀌어도 API는 그대로다. 응답이 겹치지 않고 모듈 경계를 넘지 않는다.
  - 본사 API는 경로 규칙 한 줄로 막을 수 있다. 호출자에 따른 응답 차이가 경로로 드러난다.
- **감수하는 것**
  - 클라이언트 호출 수가 늘고 조립 코드가 생긴다. 조합한 정보는 한 시점의 일관된 스냅샷이 아니다.
  - 상품 조회가 본사용과 점주용 두 경로에 있다.
- **후속 작업**: 인증 방식이 정해지면 요청자의 매장 판별과 401/403 형식을 API 명세에 반영한다.
